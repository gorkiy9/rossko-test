# Правила работы над прототипом

Сводка обязательных правил для всех, кто собирает или правит прототип. Продуктовые правила и их обоснование — в [spec.md](spec.md); этот документ переводит их в правила реализации. При расхождении источником истины считается `spec.md`.

## 1. Источники и приоритет

1. [spec.md](spec.md) — требования: сценарии A–E, тексты, цены, состояния, логика.
2. [../CLAUDE.md](../CLAUDE.md) — что собрать и критерии готовности.
3. Прод (`../src`) — реализация. Токены — в `src/index.css`.

Макеты мобильных экранов и UI Kit — в Figma (файл «Rossko — Тестовое»). Документация описывает прод, прод сверяется с документацией и макетами.

### Документация и прод

- Главное в проде — сценарии A–E, которые решают задачу: поднять долю умных курьеров, показав их пользу для конкретной корзины, и не потерять конверсию и честность выбора. Их логика, цены и тексты не меняются без запроса.
- Детали интерфейса (раскладка, состав страниц, вспомогательные функции вроде самовывоза или промокода) могут меняться в проде. Любое такое изменение в том же шаге отражается в `spec.md` (разделы «Экраны и состояния», «Тексты интерфейса») и, если затронута приёмка, в [acceptance.md](acceptance.md). Правка только в коде не считается законченной.
- Данные сценариев (товары, цены, причины, услуги, подтверждения, подсказки) в `src/data.ts` и в разделе «Тексты интерфейса» spec совпадают дословно.

## 2. Контент

- Тексты, цены, имена курьеров (Алексей, Марк, Ника) и названия товаров — из spec.
- Персональные данные, адреса, номер заказа, пункты выдачи и промокод — вымышленные моки (spec, «Вымышленные данные»). Новые бренды и логотипы не добавлять.
- Кнопки называют действие: «Перейти к оформлению», «Оплатить 36 280 ₽», «Выбрать этот слот». Без «Далее» и «ОК». Исключение — «Подтвердить заказ» при оплате при получении: денег в этот момент не списывают.
- Тон игровой и дружелюбный. Без оценок людей и сравнения курьеров между собой («умный лучше» — нельзя).
- Цены форматируются через `fmt()`: `n.toLocaleString('ru-RU') + ' ₽'` → `36 280 ₽`.
- Строка курьера в сводке: ничего не выбрано — «Курьер — не выбран», умный — «Бесплатно», платный — `+199 ₽` / `+499 ₽`.
- Подтверждение после выбора — «Отлично, » + текст по типу курьера (spec, «Тексты интерфейса»).

## 3. Честность выбора (жёсткие запреты)

- Оба основных типа видны сразу и в одинаковом размере. Красивого не прятать, не сворачивать, не уменьшать.
- Смена курьера — один клик/тап. Никаких подтверждающих модалок, «вы уверены?», задержек.
- Нет ложного дефицита: «осталось 2 курьера», таймеры, счётчики.
- Предвыбор умного и бейдж — только в «сложной» корзине, и всегда с причиной с названием товара.
- Недоступный на слот тип не прячется: карточка неактивна + ближайший слот + кнопка «Выбрать этот слот».
- После выбора красивого в сложной корзине — одна спокойная строка-подсказка, без давления (состояние E). Для кофемашины — «С подключением поможет инструкция в коробке», для кроссовок (D) — «Вернуть неподошедшее можно в пункте выдачи».

## 4. Логика выбора курьера

Повторяет раздел «Данные и логика рекомендации» spec. В прототипе данные сценариев заданы готовыми объектами в `src/data.ts` (`SCENARIOS`), производные значения считает `useOrder()` в `src/store.tsx`:

1. Предвыбор — `scenario.def` (`''` — без предвыбора, состояние B). Ручной выбор пользователя хранится в `state.sel` и важнее предвыбора.
2. Бейдж показывается, только если у сценария есть `reason`.
3. Услуги умного на карточке — `scenario.services`, не более 3.
4. Доступность красивого берётся из слота: в сценарии C он доступен только на `BEAUTY_NEAREST_SLOT` (завтра, 14:00–16:00).
5. «Выбрать этот слот» за одно действие меняет слот на «завтра, 14:00–16:00», делает красивого доступным и выбирает его.
6. Итог = товары − скидки − промокод + цена выбранного типа. Цены типов: умный 0, красивый 199, премиум 499. Пересчёт мгновенный.

Все данные — моки в одном месте (`src/data.ts`), без «магических» чисел в компонентах.

## 5. Состояние и навигация

- Маршруты (HashRouter): `#/cart` → `#/checkout` → `#/tracking` → `#/rating`. Адрес, слот, курьер, получатель и оплата — секции одной страницы оформления. Вернуться из оформления в корзину — ссылка «Изменить» в сводке.
- Одно общее состояние заказа: корзина, адрес, слот, курьер, итог. Выбор курьера отражается на сводке, трекинге и оценке. Состояние хранится в `sessionStorage`.
- Сценарий читается из параметра `s` (`#/checkout?s=C`); смена сценария сбрасывает состояние заказа к начальному для сценария.
- Панель «Сценарий» плавает в левом нижнем углу, на каждом экране показывает его сценарии и не перекрывает основные кнопки.

## 6. Доступность

- Карточки курьеров — `<button role="radio" aria-checked>` внутри `role="radiogroup"`. Тот же подход у адресов, дней, слотов и способов оплаты. Не смешивать с `aria-pressed`.
- Работают Tab, Space, Enter (у `<button>` — из коробки).
- Видимый фокус (`:focus-visible`), не убирать `outline` без замены.
- Неактивная карточка красивого (C) — не кнопка и не в порядке табуляции; кнопка «Выбрать этот слот» внутри неё доступна.
- Подтверждение выбора («Отлично, Алексей подключит кофемашину») — в контейнере с `role="status"`.
- Кнопка оплаты без выбранного курьера активна: по нажатию блок курьера подсвечивается, ошибка «Выберите, кто привезёт заказ» в `role="alert"`, страница прокручивается к блоку.
- Декоративные иконки — `aria-hidden="true"`, иконки-кнопки — с `aria-label`.
- Контраст текста — не ниже WCAG AA; высота кнопок — от 44 px.

## 7. Адаптив

- ≥ 960 px — две колонки: секции оформления слева, сводка «Ваш заказ» с кнопкой оплаты справа.
- < 960 px — одна колонка, сводка под секциями, кнопка оплаты — в фиксированной нижней панели с итогом.
- < 600 px — телефонная раскладка.
- Нет горизонтального скролла на всём диапазоне 375–1440 px.

## 8. Код

- Стек: Vite + React + TypeScript. Токены (цвета, радиусы, отступы, шрифт Inter) — CSS-переменные в одном месте (`src/index.css`), без хардкода hex в компонентах.
- Новый интерфейс в `../src` собирается в первую очередь из компонентов BoardUI (MCP `boardui`: `list_components`, `get_component`, `get_usage_examples`, `install_components`). Если подходящего нет — свой компонент. 21st.dev не используется. Существующие экраны ради BoardUI не переписываются.
- Адаптируя компонент BoardUI: `init_boardui` и `install_rules` не запускать (глобальные стили с preflight и чужие правила); компонент кладётся в `src/components/ui/`, иначе Tailwind не увидит его классы; семантические токены BoardUI (`text-text-primary`, `bg-background-*`, `border-border-*`, `text-title-*` и т. п.) заменяются токенами проекта из `src/tailwind.css`; `cx` → `cn` из `src/lib/utils.ts`; иконки Remix заменяются иконками проекта. Pro-компоненты — только с лицензией пользователя, ключ не придумывать.
- Tailwind v4 подключён без preflight (`src/tailwind.css`), чтобы не ломать экраны на обычном CSS. Классы ссылаются на токены; без произвольных hex и arbitrary values вне сетки 4 px.
- Адаптируя любой компонент: тексты — из spec, доступность — по разделу 6, анимации — без `transition-all`, пульсаций и пружин, иконки — линейные.
- Создавая или меняя интерфейс в `../src`, применять скилы:
  - `unslop:unslop` — чтобы интерфейс не выглядел сгенерированным: отступы, цвет, иконки, типографика, детали, анимация.
  - VectorLab (`vectorlab-ux-skills:*`) — по теме задачи: `spacing`, `typography`, `colour-palette`, `forms`, `labels`, `keyboard`, `surfaces`, `loaders`, `empty-states`, `motion`, `transitions`, `reduced-motion`, `viewports`, `errors`, `verbs`, `icon-buttons`, `defaults`, `anti-slop`, `page-patterns`. Перед сдачей экрана — `vectorlab-ux-skills:ux-audit`.
  - Приоритет при расхождении: spec (сценарии, цены, тексты) и правила честности выбора → токены `src/index.css` → советы скилов. Скилы не меняют тексты из spec, не вводят новые цвета и шрифты вне токенов, не генерируют картинки и логотипы. Если совет скила меняет интерфейс, изменение вносится и в spec (раздел 1).
- Прочие UI-библиотеки (MUI, Ant Design и т. п.) не используются; роутер — только `react-router-dom`.
- Один экран — один компонент в `src/screens/`, переиспользуемые элементы — в `src/components/`. `legacy/` — старые пошаговые экраны, в сборку не входят.
- Строгий TypeScript, без `any`. `npm run build` и `npm run lint` проходят без ошибок.
- Бэкенда и сетевых запросов нет.

## 9. Перед сдачей

Пройти [acceptance.md](acceptance.md) целиком на 375, 768, 1024 и 1440 px. Прогнать `vectorlab-ux-skills:ux-audit` по изменённым экранам и исправить найденное в рамках раздела 8. Сверить, что spec описывает то, что видно в проде.
